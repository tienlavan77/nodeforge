# Plan — Coder explanation and adjudicated review disputes

## Decision and current gap

Coder supplies an **initial explanation with the first `report_done`**. Reviewer must read it before issuing any finding. After findings, Coder may respond by `finding_id` without pretending to have fixed the issue; Reviewer independently adjudicates against the exact code and evidence. Supervisor persists and enforces those decisions, never decides the dispute itself. An unresolved dispute goes to human review, never auto-approval.

Current wiring differs: `backend/src/tools/agent-report-tool.js` calls `reviewFindings.assertResolved()` before saving the report and accepts Coder `finding_resolutions` as store status; `ticket-review-findings.js` treats `fixed` as the only nonblocking status and creates findings from strings. `review-worker.js` prompts with ticket, verification, patch and changed files but not Coder report/responses. `nodeforge-task-integration.js`, `review-request-handler.js`, `supervisor-loop.js`, `ticket-resume.js` and `review-revision-resume.js` need coordinated changes; `schemas/agent/tools/report-done.schema.json` and `backend/src/tools/claude-sdk-forge-tools.js` are both tool-schema surfaces. Existing tests expecting Coder `fixed` to unblock must be migrated. This plan does not declare implementation or tests complete.

## Contract and identity

- First `report_done` (and each subsequent revision report) contains `summary`, `acceptance_criteria` addressed, `implementation_scope` (`changed_files`, `not_changed_files`, `scope_rationale`), `evidence` (typed references/results), and `reviewer_notes` (`topic`, `position`, `rationale`, `evidence_refs`). `reviewer_notes` is proactive explanation, **not** a response to a finding. Keep lab/legacy behavior only behind explicit compatibility rules; never silently fabricate explanation.
- New `respond_to_review` is a separate Coder tool, available while findings are open and before another `report_done`: `{ responses: [{ finding_id, position: "accept"|"dispute", rationale, files, evidence_refs }], review_commit_sha, artifact_id, source_revision }`. Permit multiple finding responses, dedupe by request/idempotency key; preserve each version verbatim. `accept` acknowledges a finding, does not close it. `dispute` requests adjudication, does not mark `fixed` or `not_applicable`. A response can cite verified unchanged files, so do not demand edited paths for disputes.
- Reviewer finding must specify `acceptance_criterion` (exact criterion or ID), `failure`, `evidence_refs` tied to inspected material, `minimum_change_scope`, and, when more than one file is demanded, `per_file_necessity` (path and concrete role). A count of files in acceptance text alone is not proof that every file must be edited. Reject missing/empty fields at the verdict validation and persistence boundaries; no string-only findings for new reviews. Supervisor allocates stable `REV-n` IDs and preserves original text/evidence, including repeated/refined findings.
- Reviewer adjudication by `finding_id`: `retain|refine|withdraw|not_applicable|fixed`, with nonempty `reason`, checked `evidence_refs`, `reviewer_id`, timestamp, `review_commit_sha`, `artifact_id`, and `source_revision`. `refine` appends a revised scope/evidence record without erasing the original; `retain` keeps blocking. Only independent Reviewer `withdraw`/`not_applicable` or Reviewer-confirmed `fixed` closes a required finding. An `approved` verdict is valid only when all required findings have a recorded nonblocking decision for the reviewed identity. For a revision that fixes code, Coder claims repair and Reviewer verifies it against the new passed artifact; no Coder-supplied status changes the gate.
- Bind initial report, responses, finding history and adjudication to `task_id`, context/source revision, commit SHA, artifact ID and (where available) manifest SHA. Reject adjudication if context or passed artifact differs **both before dispatch and again before persisting any verdict**, not just on approval. If source changes mid-review, reverify and re-review; retain old evidence as history, do not promote its decision to the new revision. Escape/redact sensitive data before prompt dispatch; preserve a durable raw-equivalent audit record under existing access controls, with bounded prompt references if too large.

## Operating sequence and owners

1. **Schema + adapters:** implement report and response schema in `schemas/agent/tools/`, the parallel Zod/provider tool definitions (`backend/src/tools/claude-sdk-forge-tools.js`, `backend/src/tools/index.js`), and Reviewer verdict parser/validator in `review-worker.js`. Evolve old string-finding records with explicit legacy handling: keep them blocking until new evidence-backed adjudication or human disposition; do not silently withdraw. Update capability allowlists and governance for both provider paths and revision resume; keep `respond_to_review` nonterminal.
2. **Durable submission:** `report_done` checks committed revision and passed artifact, validates scope/verification, persists full input first to a revision-keyed record, and then signals handoff; it must not gate on existing open findings. Do **not** equate successful report submission with ticket acceptance: terminal completion/integration remains behind adjudicated `assertResolved()` and a matching approved verdict. Avoid applying the existing final-report `completed` status or eval-case side effects to an unapproved submission; rename/separate submission receipt from terminal report. Reconcile `ticket-resume.js` and provider completion detectors which currently use `report_done` as terminal Coder-turn marker. Retain existing immutable commit/verification safeguards, not a new manifest/checksum hunt.
3. **Response storage:** extend `ticket-review-findings.js` (or adjacent ticket-scoped durable log) with append-only `coder_responses` and `adjudications`, locked atomic writes, version/CAS, and idempotency keys; validate known finding IDs, actor, artifact and context identity. Persist response **before** enqueuing review, so restart/duplicate delivery replays the same response, not a second decision. Provide a read-only durable snapshot of `prior_coder_report`, `finding_responses`, `finding_history` for dispatch.
4. **Review orchestration:** change `nodeforge-task-integration.js`, `review-request-handler.js` and `supervisor-loop.js` to dispatch first review only after successful initial report submission, and later review after response or new verified revision. `review-worker.js` receives original report (including summary and notes), responses verbatim, history, ticket, exact commit, diff and artifact. Prompt order: read Coder explanation, inspect code/evidence, then issue findings or adjudicate each pending response with reason. Do not turn a disputed finding into a forced repair round before adjudication. Carry durable context through queue, checkpoint and `review-revision-resume.js`; rehydrate from store rather than trusting queue-only snapshots.
5. **Gate / deadlock:** pending `dispute` stays blocking but allows `respond_to_review` and a revision report; `retain`/`refine` asks for correction or further evidence on same ticket; `withdraw`/`not_applicable` closes without code changes; `fixed` requires Reviewer confirmation on a verified newer revision. Call `assertResolved()` only at acceptance/integration (or to test readiness), not before persisting explanation/response. Missing Reviewer, invalid evidence, unresolved disagreement after a bounded adjudication budget, or repeated contradictory decisions => `needs_human_review` with full audit trail, no infinite retry, no claim release/approval as if resolved. A human decision must be explicitly recorded under separate authority, not forged as a Reviewer verdict.

## Acceptance tests and rollout

Implement focused unit, integration and restart tests in `backend/tests/`:

1. Initial `report_done.summary`, scope, evidence and `reviewer_notes` are durably saved and appear in **first** Reviewer prompt before any finding is produced; revision prompt includes `prior_coder_report`, exact response text and history.
2. Open finding accepts `dispute` via independent tool even though `report_done`/terminal acceptance would be blocked; response alone never closes or approves it.
3. Reviewer `withdraw`/`not_applicable` with reason unblocks `assertResolved()`; `retain`/`refine` remains blocking and returns actionable revision guidance; claimed `fixed` without Reviewer confirmation stays blocking.
4. Restart after report persistence, response persistence, and adjudication persistence preserves identities, original text, history and exactly-once review routing; duplicate events remain idempotent.
5. Reject findings without concrete acceptance criterion, failure/evidence or minimum scope; multi-file demands without per-file necessity fail validation. Challenge of file-count reasoning must receive reasoned adjudication.
6. Reject stale artifact/commit/source or changed files on initial finding, retain, withdraw, fixed and approval; no stale verdict is persisted as current. Exercise review-worker provider and read-only tools plus resume path.
7. Exercise bounded disagreement / Reviewer unavailable => human review, retained claims/evidence, no false approval. Migrate old tests and legacy string findings deliberately; run schema validation, focused unit/integration tests and production-path canary before removing compatibility adapters.

**Implementation order:** contract/schema + durable submission → response tool/store → Reviewer prompt/verdict validation → Supervisor routing/gate/resume → tests/migration/canary. Each stage requires independent review; no acceptance based solely on updated role prompts. Invariant: Coder may petition, Reviewer adjudicates, Supervisor executes only audited decisions.
